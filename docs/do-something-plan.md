# Do Something 产品与开发实施方案

版本：0.1  
整理日期：2026 年 11 月 9 日  
适用对象：产品负责人、合作开发者、AI 编程工具  
用途：把已形成的产品方向转成可讨论、可实施和可验收的比赛原型。

## 1 项目定位

Do Something 是暂定工作名。产品希望帮助人们去做一直想做、却总留到明天的事：读书、给家人做饭、见朋友、远行、追梦。每个人可以独立行动，在自愿分享的范围内，因相似经历看见他人，形成不经意的连接。

它不以寻找搭子、建立好友关系或监督打卡为核心。用户先去生活，再选择是否留下记录、让自己的经历与其他人的经历相遇。完成后的链接也不必转化为关注、私聊或组队。

**核心体验：选择一件想做的事 → 按自己的方式行动 → 自报完成 → 留下可选记录 → 自愿分享 → 看见相似经历的回响。**

### 产品表达

以下表达来自前期讨论，可作为设计与路演参考，不是必须全部使用的品牌文案：

- 每个人独自行动，但不是孤立地行动。
- 我们可能不认识，也没有一起行动，但我们都回应了同一个约定。
- 很多事情，我们不是不想做，而是总觉得明天再做。也许一个轻轻的约定，就能让我们迈出第一步。
- 人本身是值得的；做成一件事，是值得被看见的另一件事。
- 链上的共识，是网络如何认可一份记录；人与人之间认同一个主题、愿意为它行动，是另一种共识。

产品不能传递“只有完成了，你才值得；没有完成，你就不够好”的信息。区块链记录不能替代生活的真实性，也不会自动创造人与人的共识。

## 2 已明确的方向与尚未决定的事项

### 已明确的方向

1. 面向希望把生活愿望变成行动的个人，不以组织者管理工具为主定位。
2. 用户可以独自完成，不强制寻找搭子。
3. 活动可以涵盖阅读、饮食、与家人相处、见朋友、旅行与个人梦想。
4. 日常活动在一定范围内信任用户自报，不默认要求照片、定位或第三方证明。
5. 用户完成相似活动后，有机会看见彼此并形成连接。灵感包括《你的名字》的偶然交汇与《死亡搁浅》的异步连接。
6. 每完成一次活动，希望在链上保留一条不包含正文的完成凭证。
7. 真实文本、用户资料及内容关联放在中央服务器，支持删除和注销。
8. 不希望直接给参与者分钱。积分兑换阅读权益、服务或实物是后续探索方向。
9. 产品不宜过度目的化。行为、记录和连接本身有价值，不必全部变成竞争和排名。

### 尚未决定

| 事项 | 当前状态 | 开发前建议 |
| --- | --- | --- |
| 凭证 A | 尽量少关联个人，平台登记随机编号 | 与 B 比较后选一个比赛实现，不同时开发 |
| 凭证 B | 用户可带走、证明归属的个人凭证 | 需明确钱包或签名绑定及公开关联风险 |
| 完成是否默认上链 | 已希望逐次留凭证，知情与选择流程未定 | 上链前展示不可删除范围，不在后台静默执行 |
| 积分和真实奖励 | 有愿景，尚未定规则与合作 | 不纳入核心 MVP，不接真实交易或兑换 |
| 相似经历的呈现方式 | 已明确希望发生偶然连接，具体机制未定 | 首版用活动类别匹配，自愿公开，暂不做 AI 推断 |
| 正式名称 | Do Something 为工作名 | 正式发布前检查商标、域名和应用商店重名 |
| 技术栈与开发分工 | 未最终选定 | 以队伍最熟悉的技术为准，不为概念换栈 |

本文以下流程、字段和排期属于实施建议，不应被当作用户已经逐项确认的规格。

## 3 首版的产品边界

### 建议做的内容

- 3 至 4 张预设主题卡，表达产品的生活范围。
- 1 条真正可运行的主题流程，例如“做一道一直想尝试的菜”。
- 两个演示账户，各自完成同一主题，不需要先认识或建立关系。
- 一段可选的完成感受，以及明确的私密／愿意分享选择。
- 每次完成生成一条测试网凭证，内容不含正文。
- 完成后发现一条对方主动分享的相似经历。
- 查看自己的记录，撤回分享，删除内容。
- 简单的账户删除演示，准确呈现链下与链上的删除边界。

### 首版暂不做

- 陌生人匹配大厅、即时聊天、关注系统、复杂推荐算法。
- 连续打卡惩罚、公开失败榜、完成度排名或信用分。
- 真实资金、押金、可交易代币、真实积分兑换商城。
- 微信读书、健身平台的真实自动接入，除非已经取得可用接口与相应授权。
- AI 判断现实行为真假，或根据照片自动认证亲情、健康、阅读理解。
- NFT 市场、跨链、零知识证明、大规模匿名身份系统。
- 生产级合规认证、第三方安全审计或“数据已彻底匿名”的承诺。

**比赛实现以一个真实闭环为优先。其他主题可以是可浏览的预设内容，不得伪装成已完成的集成。**

## 4 用户流程与页面

### 4.1 发现主题

首页展示主题、简短邀请和建议时长，不显示倒计时压力或全站排名。建议示例：

- 给在乎的人做一道菜。
- 去见一个你一直想见的人。
- 读完一本想读的短书。
- 去一个一直想去的小地方。

涉及家庭关系的活动允许替换对象，不默认每位用户都适合与父母互动。饮食和运动主题不提供未经专业支持的健康承诺。

### 4.2 接受一个约定

详情页说明：准备做什么、什么算完成、是否有期限、凭证记录什么。用户可加入、暂存或离开，不因未完成受到公开评价。

“约定”是产品中的共同参与规则；智能合约是记录和执行程序，两者不自动等同于法律合同。

### 4.3 完成与记录

用户点击“我完成了”，可留一句感受，也可不写。首版不用证明材料。

界面分开表达两件事：

- 活动完成：由用户自行声明。
- 凭证状态：是否已发送到链上、是否确认。

交易失败不能把用户已经做成的事变成“未完成”。链上应使用“完成声明已登记”之类准确文案，而不是“已验证真实完成”。

### 4.4 自愿分享

建议默认仅自己可见。用户可以单独选择“允许完成相似活动的人看到这段话”。这项许可不能被加入活动或生成凭证自动替代。

用户可撤回分享。撤回后停止向新访问者呈现；已经被他人截图或复制的内容不能保证收回。首版不采集精确位置，不展示准确生活发生时间和真实姓名。

### 4.5 经历相遇

完成某主题后，从同一主题下、仍有效且有分享许可的内容中选一条。

- 排除本人记录。
- 只读取已获授权的共享文本。
- 没有可展示内容时诚实留白，不制造假用户或假故事。
- 演示种子数据明确标注为示例内容。
- 建议允许一句轻回应，例如“我也做到了”；是否做回应功能可在开发时按时间取舍。

首版按主题匹配即可。未来如引入语义匹配，只处理用户允许用于推荐的内容，不读取私密记录来制造“偶遇”。

### 4.6 我的记录与删除

展示我的参与、完成声明、正文可见性、凭证状态和交易链接。允许撤回分享、删除正文和注销账户。

删除操作必须让用户知道：服务器可控的数据可以删除，已确认的公开链记录、交易时间和相关地址不能由平台单方面抹除。

## 5 链上与链下的职责

### 5.1 链上凭证能证明什么

链上记录可以证明某个声明编号被登记，或某个账户作出了一次声明。它不能独立证明用户真的做饭、见朋友、读懂一本书，也不能证明关系因此改善。

如果由平台代为提交，凭证还依赖平台诚实地登记。第三方可核验“平台提交了这条记录”，不等于第三方验证了现实行为。

每条凭证应明确属于“自报完成”，不要将其与未来的“合作方确认”混为同一认证等级。

### 5.2 凭证 A 的候选实现

平台后端生成不可预测的随机编号，例如随机 32 字节值，再由受限的提交账户登记到测试网合约。

建议链上最小数据：凭证编号、登记存在状态，以及链本身产生的交易元数据。不要默认加入活动名、用户编号、个人钱包、正文 URL、图片地址或 IPFS CID。

链下保存凭证编号与用户、活动、正文的映射。删除映射后，平台应无法再通过正常业务查询关联回该用户。若其他人此前获得对应关系，平台不能保证其也失去关联能力。

优点：普通用户不必直接使用个人钱包；公开信息较少。限制：凭证主要证明平台登记行为；若映射和用户持有的副本都删除，之后不能保证认回具体活动或本人。

**这是候选实现，不代表已决定采用 A。**

### 5.3 凭证 B 的候选实现

用户用钱包或其他签名机制持有归属证明，可以在离开平台后向他人出示。公开钱包绑定与仅在出示时披露的绑定是不同方案，不能混称匿名。

优点：用户可独立持有、核验凭证。限制：钱包地址不等于现实身份；公开地址与时间可能被关联；注销不能删除历史绑定。钱包体验和密钥管理也增加一天原型的工作量。

**这是待选方向，不在第一轮同时实现两套。**

### 5.4 合约建议接口

A 方案的最小合约可以仅提供：

- `registerReceipt(bytes32 receiptId)`：受限提交者登记未存在的编号。
- `exists(bytes32 receiptId)`：查询编号是否已登记。
- `ReceiptRegistered(bytes32 receiptId)`：记录事件，不携带用户正文。

约束：拒绝零值、拒绝重复编号、拒绝未授权调用。管理密钥仅保留在服务端，不进入前端、日志、公开仓库或用户文档。比赛只使用专门的测试账户，不使用真实资产钱包。

若采用 B，应另定签名验证、nonce、chainId、合约域、过期及重放防护，不应在 A 的说明下悄悄增加公开用户地址。

正文修改、撤回分享和删除，都不调用合约修改旧正文，因为正文从未上链。若未来需要撤销凭证，撤销是增加状态，不等于删除历史；首版可暂不实现。

### 5.5 中央服务器是合理的组成部分

服务器承担登录、私密内容、授权、匹配和删除。这样的架构不是“全部去中心化”，也不应如此宣传。

链的独特价值需要通过实际需求验证：例如由不同社区核对某条完成声明曾经存在。若未来所有验证都只在本平台内部发生，普通数字签名和数据库可能已经足够；不要仅用交易数量证明产品价值。

## 6 数据与 API 草案

建议首版不收手机号、住址、生日、健康数据或第三方账号密码。采用演示账户或项目已有的成熟登录方案。演示账户也必须做服务端隔离，不能相信前端传入的任意 `userId`。

### 数据对象

| 对象 | 建议主要字段 | 约束 |
| --- | --- | --- |
| User | id、displayName、status、createdAt | 昵称可选，账户删除后不能登录 |
| Activity | id、title、description、category、ruleVersion、status | 已有人加入后不得静默改规则 |
| Participation | id、userId、activityId、ruleVersion、status | 首版每用户每主题只保留一次参与 |
| Completion | id、participationId、declaredAt、verificationType | 首版 verificationType 为 self_report |
| Reflection | completionId、text、visibility、sharedAt、deletedAt | 默认 private，读取前强制检查权限 |
| Receipt | completionId、receiptId、chainId、contractAddress、txHash、status | 随机编号在服务端生成，确认前不称成功 |
| Reaction | id、senderId、reflectionId、type | 可选项；撤回或删除内容后不可继续访问 |
| DeletionRequest | id、userId、status、requestedAt | 生产版需要明确备份处理及例外保留规则 |

`Receipt` 状态建议为 `not_requested → queued → submitted → confirmed`，失败另设 `failed`；交易回执未确定时不得直接认定失败或重新生成一条完成记录。

### API 草案

- `GET /activities`：公开主题列表。
- `GET /activities/:id`：主题与当前规则。
- `POST /participations`：当前用户接受主题约定。
- `POST /participations/:id/complete`：创建自报完成，使用幂等键。
- `PUT /completions/:id/reflection`：仅本人编辑正文和分享许可。
- `POST /completions/:id/receipt`：知情后申请登记；同一完成不得重复登记。
- `GET /completions/:id/receipt`：本人查询状态和交易链接。
- `GET /echoes?activityId=...`：仅返回可分享且未删除的合格记录，不返回私密字段。
- `DELETE /completions/:id/reflection`：删除正文及分享资格。
- `DELETE /account`：撤销会话、禁止新操作并处理账户关联删除。

这些接口名是开发草案。开发者可按现有框架调整，但必须保留权限、幂等和分享边界。

### 交易与删除的并发处理

- 未广播的登记任务：用户删除后取消队列任务。
- 已广播的交易：不能承诺取消；删除链下内容与关联，并提示交易仍可能确认。
- 重试：先按既有 `receiptId` 查询链上状态，避免重复登记。
- 恢复备份：生产系统应重放删除请求，避免已删除账户复活。

## 7 开发顺序与比赛排期

### 7.1 技术选择建议

优先使用团队最熟悉的 Web 技术。一个可选组合是 TypeScript 前端与后端、轻量关系数据库、Solidity 合约，以及熟悉的 EVM 调用库和测试框架。不必为了比赛额外引入微服务、向量库或 AI Agent。

将链上操作封装成 `ReceiptProvider`，先实现明确标注的本地模拟，再替换为 Monad 测试网适配。模拟模式与真实测试网模式必须在 UI 上可区分，模拟交易不能展示成真实链上凭证。

建议代码结构：

```text
app/                  页面与交互
server/               身份 权限 内容 分享 删除
contracts/            最小凭证合约与测试
lib/receipt-provider/ 模拟与测试网适配
fixtures/             清楚标注的演示内容
README.md             启动 环境变量 模式说明
DECISIONS.md          已决定与待决定事项
TEST_PLAN.md          验收清单
```

### 7.2 第一轮可先开始的工作

即使 A／B 还没决定，也可以先做：主题页、参与流程、自报完成、私密正文、分享开关、相似经历展示、链下删除、凭证适配接口及本地模拟。

真正写入公链前，须选定凭证模型和知情文案。真实第三方接入、收费、礼品采购与生产发布不在本次整理所授予的执行范围内。

### 7.3 六点五小时原型排期

| 时间 | 工作 | 完成标准 |
| --- | --- | --- |
| 0 至 0.5 小时 | 确定唯一场景、凭证方案、演示账户和技术栈 | 画出完整流程，环境能运行 |
| 0.5 至 2 小时 | 前端与后端并行；另一人做最小合约 | 两账户独立完成；合约通过基础测试 |
| 2 至 3.5 小时 | 分享过滤、相似记录、链下删除 | 私密内容绝不出现在发现流 |
| 3.5 至 4.5 小时 | 测试网部署与凭证联调 | 一次真实测试网登记，页面正确显示回执 |
| 4.5 至 5.5 小时 | 权限、重复提交、失败与删除测试 | 关键验收通过，不新增功能 |
| 5.5 至 6 小时 | 路演、备用录屏、README 与提交材料 | 从零跑通演示，保存真实回执 |
| 最后 0.5 小时 | 按主办方实际入口提交并核验 | 确认项目、队伍、文件及提交回执 |

如只有一名开发者，进一步减少页面和交互；优先保留“完成 → 自愿分享 → 相似经历 → 真实凭证”闭环。不要以删除权限测试来换取商城或动画。

## 8 验收清单

### 产品体验

- [ ] 用户无需寻找搭子或建立好友关系，即可参与和完成。
- [ ] 完成声明与正文分离；可以不写故事。
- [ ] 分享默认关闭；开启与撤回均清楚可见。
- [ ] 展示真实获准内容，或明确标记的演示样例；不编造“有人因你改变”。
- [ ] 无内容时显示空状态，不诱导用户公开隐私。
- [ ] 未完成、退出和延后不触发羞辱性文案或公开排名。

### 数据安全与删除

- [ ] 用户 B 无法读取、修改、删除用户 A 的私密记录。
- [ ] 撤回分享后，发现接口不再返回该内容。
- [ ] 删除正文后，数据库读取和展示缓存均不再提供它。
- [ ] 注销后会话失效，队列不会继续为已删除用户创建新的登记。
- [ ] 文本按安全方式展示，防止脚本注入；服务端限制长度并校验参数。
- [ ] 不在日志、错误上报或链上参数中记录私密正文和密钥。
- [ ] 删除文案准确说明公开链、备份和已被他人复制的边界。

### 链上功能

- [ ] 真实测试网、模拟模式和失败状态明确区分。
- [ ] 凭证不包含姓名、故事、活动内容 URL 或其他未经决定的字段。
- [ ] 重复点击只产生同一条业务完成记录和同一凭证编号。
- [ ] 非授权调用被拒绝；重复凭证不会重复创建。
- [ ] 超时后先查询既有交易／凭证，不盲目重发。
- [ ] 区块浏览器链接使用正确网络及真实交易哈希。
- [ ] 链下删除之后，界面不声称已删除链上历史。

## 9 路演脚本与验证目标

### 九十秒演示建议

1. “有些事，我们总想做，却总留到明天。Do Something 给出一个轻轻的约定。”
2. 账户 A 独自加入主题、完成并留下一句愿意分享的话。
3. 登记一条不含正文的测试网完成凭证，展示真实回执。
4. 账户 B 在自己的时间完成同一主题，看见 A 主动分享的经历。
5. “他们没有预先匹配，也不需要成为好友，但两段生活有了一次交汇。”
6. 展示撤回分享或删除正文，说明可删除的生活内容与不可删除的链上记录之间的边界。

不要宣称区块链验证了真实行为、实现绝对匿名，或该产品只有 Monad 才能实现。

### 原型要验证的三件事

- 一张活动卡是否让人愿意开始一件原本拖延的小事。
- 看见相似经历，是温柔的连接，还是新的社交压力。
- 用户是否理解并愿意选择生成公开且不可抹除的完成凭证。

初期观察完成与分享的自愿程度、隐私理解、重复使用意愿即可。不能用链上交易数代替用户价值，也不能凭小样本声称改善了拖延或家庭关系。

## 10 后续产品演进

### 阅读与健身生态

未来可对接正式授权的阅读、运动服务，将合作方的完成结果与用户自报分开显示。当前未确认微信读书具备本项目可用的开放接口或合作权限，不采用抓取登录凭据、复用会话或绕过平台限制的方式接入。

### 积分与奖励

可以探索读书完成分配第一部分积分，笔记交流或投票再分配剩余积分；兑换读书卡、课程或实体书。但这些是另一个阶段，需要先确定赞助方、库存、规则、申诉、履约和退款机制。

积分可换物品并不自动排除经济价值或监管要求。购买电子书、课程等实际服务与收钱形成参与者输赢奖池不同，必须按真实业务结构审查。首版不引入真实奖品与收费，也不承诺未来空投或主网权益。

### 内容与社群安全

公开故事需要举报、屏蔽和内容处置机制，尤其要保护未成年人及家庭、健康等隐私。公开上线前应单独设计这些能力；封闭的演示原型不能被包装成可立即开放的大规模产品。

### 参考产品与名称

- Ecochallenge：共同承诺、各自行动、自报完成、集体影响。https://ecochallenge.org/ecochallenge-platform/how-it-works/
- BeKind：日常善意行动与故事分享。https://www.bekind.app/
- Slowly：异步、慢节奏的远方连接。https://slowly.app/
- 小打卡：社群行动、记录与互动。https://www.xiaodaka.com/about
- DoSomething.org：现有同名公益行动品牌，正式命名前需要查重。https://dosomething.org/what-we-do

这些是参考，不代表已经完整实测，也不能据此宣称市场空白或全球首创。

## 11 交给开发者的启动说明

> 请先阅读本方案，确认已有仓库与技术环境，再提出最小实施计划。先复述“独立行动、自愿分享、行动后连接”的产品核心，避免做成找搭子或强监督打卡平台。
>
> 第一轮实现单场景闭环：主题 → 参与 → 自报完成 → 可选正文 → 分享许可 → 相似经历。先用清楚标注的 ReceiptProvider 模拟实现，不生成假链上交易。
>
> 凭证 A／B 尚未最终决定。请在部署合约前，列出你建议采用的方案、链上字段、用户需要知道的隐私代价和开发时间，由项目负责人确认。不要为推进开发而自行把用户地址、活动名或正文哈希写入公链。
